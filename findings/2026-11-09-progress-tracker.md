# 2026-11-09 — Progress tracker: how AnyPS5's page works, and what Pirates! needs

## How AnyPS5's progress.html actually works

- The live page ([boykopovar.github.io/AnyPS5/progress.html](https://boykopovar.github.io/AnyPS5/progress.html)) is a **fully server-rendered static file**, not a JS app fetching JSON. It is generated by one script, [`tools/progress.py`](https://github.com/boykopovar/AnyPS5/blob/364ceeba2f9bc11227a62d08490640264350058d/tools/progress.py) (810 lines at commit `364ceeb` — the exact raw file I fetched), plus `tools/nid_names.py`, `tools/shader_scan.py`, and `tools/rdna_*.txt`.
- **Data source: source-tree scanning, no build.** `progress.py` walks `core/libs/prx/**/*.cpp` and regex-matches `APS5_VABI` definitions: a function counts as "implemented" when its body does **not** call the `NotImplemented_nid_no_patch` stub (plus transitive stub-wrapper/inert-body detection). Shader numbers come from the `RdnaOpcode.hpp` enum vs [`tools/rdna_isa.txt`](https://github.com/boykopovar/AnyPS5/blob/364ceeba2f9bc11227a62d08490640264350058d/tools/rdna_isa.txt). No objdiff, no build artifacts, no decomp.me — just the committed source.
- **Outputs (all files, one run):** `write_site()` emits 5 files: `progress.json` (raw numbers), `progress.html` (table, by `table()`/`summary()`), `progress.svg` (treemap), `badge-libraries.svg`, `badge-shaders.svg`. The page itself says so: "Generated by tools/progress.py on every push to `main`. Raw numbers: progress.json."
- **Update pipeline (three workflows):** [`pages-progress.yml`](https://github.com/boykopovar/AnyPS5/blob/364ceeb/.github/workflows/pages-progress.yml) runs on pushes touching `core/libs/prx/**` or the script/ISA files, runs `progress.py --require-shader-source`, diffs the new `progress.json` vs deployed via `gh api repos/.../pages`, and only if changed dispatches [`pages.yml`](https://github.com/boykopovar/AnyPS5/blob/364ceeb/.github/workflows/pages.yml) (`progress.py` + `progress_history.py` → `actions/deploy-pages@v5`). [`progress-report.yml`](https://github.com/boykopovar/AnyPS5/blob/364ceeb/.github/workflows/progress-report.yml) runs the same script base-vs-head on PRs and prints a delta to the step summary.
- Hosting is GitHub Pages (branch or custom Actions workflow — [publishing-source docs](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)); AnyPS5 uses the Actions variant. Standard hosted runners in public repos + Pages deploys are free ([Actions billing](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions)).

## How the established decomp trackers source data

### decomp.dev / decompilati.onl (objdiff report.json)

- Projects generate **objdiff** reports: `objdiff-cli report generate -o report.json`. The JSON lists per-unit matched/fuzzy/complete code and matched data; "Detailed progress reporting (powers decomp.dev)" per [objdiff README](https://raw.githubusercontent.com/encounter/objdiff/main/README.md).
- Submission: CI uploads `<version>_report` as an Actions artifact on push to main (sly1 `progress.yml`, pkmn-colosseum `GC6E01_report`); decomp.dev scanned those. decomp.dev has sunset its index ([decomp.dev](https://decomp.dev/projects)); successor [decompilati.onl](https://decompilati.onl/docs/objdiff): POST `report.json` to `/api/v1/progress?commit=…` (gzip) or its GitHub App reading a `<version>_report` artifact. Generic format: [report-format](https://decompilati.onl/docs/report-format).
- **Fit issue:** objdiff expects a real object-file diff pipeline (`objdiff.json` with `target_path`/`base_path` per unit). Our toolchain is a custom harness (COFF relocations + byte compare); we'd be faking objdiff's objects. The generic JSON POST is easy, but it loses per-function fidelity unless we emit the functions list ourselves.

### progress.decomp.club (legacy DTK/DTK-template)

- progress.decomp.club 404'd to my fetcher (dynamic), so verified via primary DTK-template repos: `configure.py` declares `Matching`/`NonMatching` + `progress_category` ([configure.py](https://raw.githubusercontent.com/encounter/dtk-template/main/configure.py)); `python3 configure.py progress` (`tools/project.py:calculate_progress()`) emits `build/<version>/progress.json`+`report.json`, uploaded via `tools/upload_progress.py -b https://progress.decomp.club/` (zeldaret/tww history). Superseded by decomp.dev.

## Recommended architecture options

**A. AnyPS5-style self-contained static page (recommended).** A small script `tools/make_progress.py` reads the *tracked* census/JSON (not Wine output) and writes `docs/progress.html` + `docs/progress.json` (+ optional SVG badge) into a committed `docs/` folder; GitHub Pages "Deploy from a branch" publishes `main:/docs`. Data flow: run census locally (or reuse the last committed census) → emit JSON/HTML → commit both. Zero CI compute, zero API keys, works for a private-but-Pages-visible repo. [INFERENCE] This is the smallest boring design: one Python file (~150 lines) reusing `compare_census.py` totals but adding per-function detail.

**B. Emit objdiff-`report.json` + decompilati.onl (compatible).** Extend the census writer to also emit `report.json` in objdiff's schema (units with matched code bytes) and either POST to decompilati.onl or upload `<version>_report` artifact. Buys community visibility, costs a schema mapping we must maintain and faking objdiff's object model we don't have. Only worth it if we want a public index later.

**C. Only ship `progress.json` (badge-only).** Minimal: a GitHub-hosted JSON consumed by shields.io (`img.shields.io/endpoint?url=…`), embedded in README. Less discoverable than a real page.

Recommendation: **A now, B's JSON format as the data shape** — i.e. emit a `progress.json` shaped like decompilati.onl's generic report (`code:{total,matching,non_matching}`, `functions:{total,matching}`, `areas` = subsystem) so a later move to B is a one-step POST. Why: our "matched" = byte-identical under `match.py`, which neither AnyPS5's source-scan nor objdiff's fuzzy scale measures natively; a schematic `matching`/`non_matching` byte count (from `functions.json` spans of PASS vs FAIL) is honest and comparable, and the per-function list keeps it auditable.

Suggested `progress.json` (generated, committed under `docs/`):

```json
{
  "unit": "functions",
  "functions": {"total": 7862, "matching": 3},
  "code": {"total": 2861115, "matching": 0, "non_matching": 0},
  "areas": [{"name": "crt", "functions": {"total": 0, "matching": 0}}],
  "commit": "<sha>", "generated": "2026-11-09",
  "functions_detail": [{"address": "0x00547610", "symbol": "FUN_00547610", "unit": "hand_x", "status": "PASS"}]
}
```
